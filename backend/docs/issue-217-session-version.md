# 이슈 #217 세션 버전 마이그레이션 및 배포 절차

공통 운영 승인, 사전 검사와 롤백 절차는 [Cathori 1.0.2 운영 전환 검토](issue-217-release-safety.md)를 따른다.

## 스키마 변경

저장소에는 별도 마이그레이션 실행기가 없다. 운영 배포 전에 승인된 대상 DB에서 담당자가 [세션 버전 추가 SQL](../db/migrations/001-add-user-session-version.sql)을 한 번 적용한다. Hibernate의 `ddl-auto` 설정에 스키마 전환을 맡기지 않는다.

1. 대상 DB와 `users.session_version` 존재 여부를 확인한다. 열이 이미 있다면 타입, 기본값, NULL 허용 여부를 확인하고 적용 이력을 대조한다.
2. `ALTER TABLE`이 테이블 잠금을 획득하므로 배포 창에 DB 잠금 대기 한도를 정한다. 대상 DB를 확인한 연결에서 다음 명령을 실행한다.

   ```sh
   psql -X --set ON_ERROR_STOP=1 --single-transaction \
     --file backend/db/migrations/001-add-user-session-version.sql
   ```

3. `information_schema.columns`에서 타입이 `bigint`, 기본값이 `0`, NULL 비허용인지 확인한다. 기존 행과 새 행에 기본값이 적용되며, SQL은 기존 `device_token`을 보존한다.
4. 구 백엔드의 요청 처리를 종료하고 신 백엔드로 전환한다. 구 버전이 기기 토큰을 계속 쓸 수 있는 혼용 구간에서는 이슈 #217의 보호가 성립하지 않는다. 백엔드 롤백 시 추가 열은 유지할 수 있지만, 구 백엔드에는 세션 버전 보호가 없다.

## 사용자 및 푸시 영향

- `sv`가 없는 기존 Access·Refresh JWT는 인증에 실패하므로 한 번 재로그인해야 한다. JWT는 기존과 같은 문자열 필드로 전달한다. 현재 프런트는 회원 API의 401에 재발급을 시도하고, 재발급도 실패하면 로컬 인증을 종료한다.
- 같은 계정으로 다시 로그인하면 새 세션이 활성화되고 이전 기기의 Access·Refresh JWT는 거부된다. 로그인은 기존 FCM 토큰을 비우므로 새 세션의 등록이 성공한 뒤부터 해당 사용자가 발송 대상에 포함된다.
- 마이그레이션만 적용하면 `session_version = 0`인 기존 행의 FCM 토큰이 발송 조회 대상에 남을 수 있다. 재로그인 전 기존 토큰의 발송을 중단해야 하는 경우, 대상 행과 푸시 중단 범위를 검토해 별도의 승인된 정리 작업으로 처리한다. 마이그레이션 파일에는 일괄 삭제가 포함되어 있지 않다.
- 로그아웃 커밋 후의 지연 등록은 서버에서 거부한다. 서버 로그아웃이 커밋되지 않았거나 발송 작업이 이미 토큰을 조회한 경우에는 기존 알림이 남을 수 있다.
- 격리된 QA 프로젝트에서 iOS·Android 각각 회원 A → 로그아웃 → 게스트 → 회원 B를 검증한다. A 토큰으로 이미 큐에 올라간 알림과 로그아웃 뒤 새로 생성한 알림을 구분하고, 포그라운드·백그라운드·종료 상태에서 수신 여부를 확인한다. 만료 Access Token, 네트워크 단절, 기기 토큰 삭제 실패도 별도로 검증한다.

## 잠금과 트랜잭션

- 로그인, 재발급, 로그아웃, 회원탈퇴는 모두 `users` 행을 먼저 잠근 뒤 Refresh Token을 변경한다. PUT·DELETE도 같은 행 잠금을 사용한다. 로그인은 잠금 안에서 비밀번호를 확인하므로 동일 계정 요청은 BCrypt 처리 동안 대기할 수 있다.
- 테스트의 PostgreSQL에서 Hibernate는 `PESSIMISTIC_WRITE`를 `FOR NO KEY UPDATE OF u1_0`으로 실행했다. `READ COMMITTED`에서 같은 행을 갱신하는 요청은 선행 트랜잭션 종료까지 기다린다. 잠금 직후 엔티티를 다시 읽어 JPA 영속성 컨텍스트에 이미 있던 세션 값으로 검증하지 않도록 한다.
- 앱의 HTTP 타임아웃과 PostgreSQL 잠금 대기 한도는 별개다. 이 변경에서 애플리케이션의 잠금 타임아웃이나 자동 재시도 정책을 추가하지 않았다. DB가 잠금 타임아웃 또는 교착 상태로 트랜잭션을 중단하면 요청은 실패하고 변경은 롤백된다. 운영에서는 DB의 대기 한도와 애플리케이션 요청 제한을 함께 확인한다.
