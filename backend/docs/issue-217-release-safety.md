# Cathori 1.0.2 운영 전환 검토

## 기존 배포에서 확인한 위험

기존 워크플로는 `main` 변경 또는 수동 실행으로 이미지를 빌드해 `latest`를 갱신한 뒤 SSH로 접속한다. 서버에서 `git pull`, Compose 이미지 가져오기와 서비스 갱신, Nginx 다시 읽기를 차례로 수행한다. 별도 마이그레이션 실행기가 없고 배포는 스키마 적용 여부를 조회하지 않았다. 운영의 Hibernate 설정도 환경 변수에 따라 달랐다. 컬럼 또는 테이블이 없으면 새 코드의 시작이나 회원·푸시 조회가 실패할 수 있고, 자동 스키마 생성만으로는 002의 기존 중복 정리와 소유권 이력 생성이 이루어지지 않는다.

이슈 #217 이전 서버는 JWT의 `sv`와 이전 소유권을 확인하지 않는다. 003을 지원하지 않는 서버의 발송 경로는 등록 확인 필드도 검사하지 않으므로, SQL만 먼저 적용해도 기존 발송을 차단할 수 없다. 같은 서명 키로 세션 검증이 없는 구 이미지에 롤백하면 폐기된 JWT가 만료 전에 다시 허용될 수 있다. 구 워크플로의 `latest` 이미지와 서버가 가져온 Git 커밋도 같은 릴리스라는 보장이 없었다.

## 승인 단계와 배포 순서

이 문서와 배포 파일은 제안된 운영 절차다. 운영 접속, 데이터 변경, 이미지 게시 및 실제 배포는 승인받은 담당자가 별도로 수행한다.

1. GitHub의 `production` 환경에 승인자, 자기 승인 제한, `main` 제한을 설정하고 운영 SSH 자격 증명을 해당 환경으로 제한한다. 저장소 설정의 보호 규칙을 확인한 뒤 수동 워크플로를 실행한다. 워크플로의 승인 확인 입력은 운영 검토를 기록하며 환경 승인 설정은 GitHub에서 관리한다.
2. 배포 창, 대상 DB·스키마, 기존 이미지 다이제스트와 복구 지점을 확인한다. 구 워크플로의 대기·실행 중 작업과 다른 운영자의 배포를 종료한다. **마이그레이션 전에** 아래 유지보수 절차를 실행해 Nginx의 API 응답이 `503`인지 확인하고, 구 백엔드의 요청과 발송 작업을 종료한다. 외부 복제본이 있다면 함께 종료한다.
3. 승인된 연결에서 [001 세션 버전](../db/migrations/001-add-user-session-version.sql), [002 소유권 격리](../db/migrations/002-isolate-device-token-ownership.sql), [003 푸시 등록 확인](../db/migrations/003-confirm-device-token-for-push.sql)을 순서대로 적용한다. [데이터 전환 절차](issue-217-device-token-ownership.md)에 따라 잠금 대기 한도, 중복 그룹 수, 영향 계정 수를 확인한다. 003은 기존 토큰과 이력을 유지하고 확인 세대를 NULL로 둔다. 이미 적용된 SQL은 정의와 적용 이력을 확인한다.
4. 승인된 `main` 커밋으로 수동 배포를 실행한다. 서버 체크아웃과 빌드 커밋을 대조하고, 해당 이미지의 다이제스트로 검증과 시작을 고정한다. 배포 스크립트는 Nginx `503`과 구 백엔드 정지를 확인한 뒤 실제 백엔드와 동일한 DB 설정으로 001·002·003 스키마와 기존 소유권 이력을 읽기 전용 검사한다. 검사 후에도 유지보수와 정지 상태를 다시 확인하고 새 백엔드를 시작한다.
5. 새 컨테이너도 애플리케이션 시작 전에 스키마를 검사한다. Hibernate는 `validate`로 시작하고, Compose는 앱 준비 상태와 DB 상태를 확인한 뒤 Nginx를 갱신한다. 스크립트 종료 시에도 API는 `503`이며, 신규 발송과 실패 재시도 스케줄러는 유지보수 마커가 있는 동안 실행을 건너뛴다.
6. 승인된 점검 경로에서 로그인, FCM 등록과 폐기, 발송 자격을 확인한다. 검증 결과와 적체 알림 처리, 푸시 재개를 승인한 뒤 마커를 제거한다. 같은 마커의 제거로 API와 발송 스케줄러가 다시 열리므로, 트래픽과 발송을 함께 재개할 수 있는 시점에 수행한다.

### 유지보수 시작과 종료

승인된 호스트의 체크아웃에서 Compose에 필요한 `CATHORI_BACKEND_IMAGE`를 기존 백엔드 이미지 다이제스트로 지정한다. 처음 전환할 때는 새 설정의 Nginx만 갱신해 유지보수 응답을 활성화한다.

```sh
mkdir -p .release-state
touch .release-state/enabled
docker compose -f docker-compose.prod.yml up -d --build --no-deps nginx
```

정상 TLS 연결에서 외부 API의 `503`과 `Retry-After`를 확인한 뒤 기존 백엔드를 정지한다. `/healthz`의 `200`은 Nginx 생존 신호다. 새 백엔드 준비 상태는 Compose가 별도로 확인한다.

```sh
docker compose -f docker-compose.prod.yml stop -t 60 backend
```

이후 마이그레이션과 수동 배포를 진행한다. 배포 스크립트에는 구 백엔드를 정지하는 단계가 없으므로, 정지보다 먼저 마이그레이션을 실행하거나 구 백엔드가 실행 중인 채 수동 배포를 시작하는 실수를 피해야 한다. Compose 밖의 복제본 정지는 운영자가 확인한다. 작업이 실패하거나 검증이 끝나지 않으면 마커를 유지한다. 재개 승인 뒤에는 `rm .release-state/enabled`로 마커 파일만 제거하고 API와 발송을 점검한다.

### 마이그레이션 적용 방식

| 방식 | 고려사항 |
|---|---|
| 배포 중 자동 적용 | 순서의 일관성은 높지만 배포 계정에 DDL·데이터 변경 권한이 필요하다. 002의 테이블 잠금과 중복 등록 해제를 무인 배포에서 처리하게 된다. 실패 시 이미지·DB 변경을 각각 판별하고 복구해야 한다. |
| 별도 승인 후 수동 적용 및 자동 검증 | **채택.** 001·002·003의 변경 범위와 중복 해제·알림 중단 영향을 먼저 검토한다. 배포 과정은 읽기 전용으로 누락과 정의 불일치를 차단한다. 적용과 배포가 다른 단계이므로 운영자가 유지보수 창과 실행 순서를 관리해야 한다. |

## 기존 FCM 등록 처리안

서명된 기존 JWT에 `sv`가 없으면 세 안 모두 첫 회원 API 요청 시 재로그인이 필요하다. FCM 등록을 유지할지와 JWT 재로그인은 별개 정책이다.

| 대안 | 알림 격리와 사용자 영향 | 발송·재시도 및 복구 | 데이터 복구 |
|---|---|---|---|
| A. 전환 시 기존 등록 전부 초기화 | 기존 등록으로 새 알림이 나가는 경로를 즉시 끊는다. 회원 전체의 푸시는 재로그인과 기기 등록이 성공할 때까지 중단된다. | 신규·대기·재시도 조회 모두 비워진 등록을 보게 된다. 재등록 실패는 기기 권한·네트워크·현재 세션 PUT 결과를 확인하고 다시 등록한다. 이미 읽힌 발송 대상은 별도로 종료해야 한다. | 초기화 전 복구 지점이 필요하다. 이전 원문을 일괄 복원하면 잘못된 소유권도 되살아날 수 있어 안전한 복구는 새 등록을 기준으로 한다. |
| B. 등록 보존 및 재등록 전 발송 제외 | **로컬 구현 완료, 운영 승인 대기.** 기존 기록을 보존하면서 003 이후 성공한 PUT으로 확인한 현재 세대와 소유권의 토큰만 사용한다. | 신규 대상 산정, PENDING 조회, 실패 재시도에 같은 자격 조건을 적용한다. 일시적인 PUT 실패는 앱이 현재 세션에서 제한적으로 재시도한다. 발송 완료로 표시된 과거 공지를 일괄 재생하지 않는다. | 보존된 행은 전환 진단에 사용할 수 있다. 자격 검사를 제거하거나 이력으로 확인 세대를 일괄 채우면 과거 등록이 재활성화된다. |
| C. 발송 일시 중단 후 단계별 재개 | 실제 푸시 발송과 재시도를 먼저 멈추고, 새 등록이 확인된 QA 또는 승인된 범위부터 점진적으로 재개한다. 중단 기간 동안 푸시 지연이 발생한다. | 신규 발송과 고정 크론의 실패 재시도까지 함께 중단해야 한다. 재개 전에 적체 알림의 만료·재처리 기준과 새 등록 실패 복구 경로를 확인한다. | 데이터 일괄 삭제 없이 진행할 수 있다. 문제 발생 시 발송을 다시 중단하고, 재개 대상을 재검증한다. |

B의 운영 적용과 발송 재개는 별도 승인 사항이다. 003은 `session_version`이나 002에서 생성한 이력으로 확인 여부를 추정하지 않는다. 기존 앱이 같은 세션을 이미 등록 완료로 기억하고 있다면 앱 재시작 또는 재로그인 후 PUT이 성공할 때까지 푸시가 중단될 수 있다. 서버는 이미 조회된 토큰이나 FCM이 수락한 알림을 회수할 수 없다.

## 실패 시 롤백과 재배포

- 사전 검사가 실패하면 스키마 오류를 수정한 뒤 같은 승인 흐름으로 다시 배포한다. 검사만 실패한 경우 배포 스크립트는 실행 중인 백엔드를 정지시키지 않는다.
- 기존 서버 정지 이후 새 서버 준비가 실패하면 트래픽과 푸시를 유지보수 상태로 둔다. 실패 컨테이너와 스키마 상태를 확인한다. 자동으로 구 이미지로 되돌리지 않는다.
- 우선 수정한 새 이미지를 배포한다. 이전 다이제스트가 필요하면 `sv` 검증, Refresh 폐기, 토큰 소유권, 003 발송 조건과 유지보수 처리까지 호환되는 이미지를 사용한다. 스크립트는 `org.cathori.push-schema-version=003`과 `org.cathori.push-ownership-policy=account-bound-v1`을 선언한 승인 이미지에만 시작을 허용한다. 해당 이미지와 호환되는 Compose에서 같은 사전 검사를 통과한 뒤 시작한다.
- 보안 호환 이미지가 없다면 회원 트래픽과 발송 중단을 유지한다. 구 이미지 사용은 별도 사고 대응 승인 대상으로 두며, JWT 키 교체와 기존 인증 무효화를 검토한다. 키 교체 뒤에도 구 이미지에는 세션 폐기 및 소유권 보호가 없다.
- 001·002·003을 자동으로 되돌리거나 기존 토큰을 일괄 복원하지 않는다. DB 복원이 필요하면 스키마, 세션 버전, JWT 서명 키, 토큰 소유권과 확인 이력이 함께 일치하는지 확인하고 복원에 따른 인증·푸시 재활성화를 별도 승인한다.

## iOS·Android QA 준비

- 운영과 분리된 API·DB·Firebase 프로젝트를 준비한다. iOS는 별도 번들 ID와 QA APNs 연결, Android는 별도 애플리케이션 ID와 QA Firebase 설정을 사용한다. 두 플랫폼의 새 네이티브 빌드에 푸시 설정을 포함한다.
- 합성 계정으로 기존 앱의 재로그인, 최초 등록 실패 후 복구, 정상·만료 Access 로그아웃, Refresh 폐기 응답 유실, A → 게스트 → B 전환을 검증한다.
- 포그라운드·백그라운드·종료 상태에서 A의 이전 등록과 B의 신규 등록에 대한 결과를 각각 확인한다. 전환 전에 이미 전달된 알림과 전환 후 새 발송을 구분하고 토큰 원문은 보고서에 남기지 않는다.
